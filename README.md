# shop_api

Невеликий REST API для вигаданого магазину. Робив, щоб розібратися, як зв'язати FastAPI з PostgreSQL без ORM, на чистому SQL через `psycopg2`. Тут є користувачі, товари і транзакції між ними: хтось купує, а API перевіряє, чи вистачає і грошей, і товару на складі.

Для реального магазину цього замало, але як навчальний проєкт працює нормально.

## Що використано

- Python
- FastAPI
- PostgreSQL
- psycopg2 (запити пишу руками)
- python-dotenv (щоб не тримати паролі в коді)

## Як запустити

Клонуємо репозиторій і ставимо залежності:

```bash
git clone https://github.com/booksya29/shop_api.git
cd shop_api
python -m venv venv
source venv/bin/activate        # на Windows: venv\Scripts\activate
pip install fastapi uvicorn psycopg2-binary python-dotenv
```

Поки що `requirements.txt` у репозиторії немає, тому ставити доводиться вручну, як вище.

Далі створюємо файл `.env` у корені проєкту:

```
DB_USER=postgres
DB_PASSWORD=твій_пароль
DB_HOST=localhost
DB_PORT=5432
DB_NAME=shop
```

База даних має існувати і в ній мають бути таблиці для користувачів, товарів і транзакцій. Скрипта, який їх створює, у репозиторії поки немає, так що таблиці треба зробити самому.

Запуск:

```bash
uvicorn main:app --reload
```

Сервер підніметься на `http://127.0.0.1:8000`. Swagger з усіма ендпоінтами, де їх можна одразу пробувати, лежить на `/docs`.

## Що вміє

### Користувачі (`/user`)

| Метод | Шлях | Що робить |
|-------|------|-----------|
| POST | `/user` | додає нового користувача |
| GET | `/user` | повертає всіх користувачів |
| GET | `/user/?user_id={id}` | повертає одного користувача |
| PATCH | `/user/{user_id}` | змінює дані користувача |
| DELETE | `/user/{user_id}` | видаляє користувача |

### Товари (`/products`)

Товар визначається за штрихкодом (`barcode`), а не за числовим id.

| Метод | Шлях | Що робить |
|-------|------|-----------|
| POST | `/products/add` | додає товар |
| GET | `/products/` | список товарів |
| PATCH | `/products/{barcode}` | редагує товар |
| DELETE | `/products/{barcode}` | видаляє товар |

### Транзакції (`/transactions`)

| Метод | Шлях | Що робить |
|-------|------|-----------|
| POST | `/transactions/new` | створює покупку |
| GET | `/transactions/show` | усі транзакції |
| GET | `/transactions/show?buyer_id=2` | транзакції конкретного покупця |

Перед створенням покупки API дивиться, чи є потрібна кількість товару і чи вистачає грошей у покупця. Якщо ні, транзакція не проходить.

## Як це все влаштовано

```
shop_api/
├── main.py             # точка входу, підключення роутерів
├── database.py         # підключення до PostgreSQL
├── ApiRouters/         # роутери: користувачі, товари, транзакції
├── database_control/   # функції для роботи з базою (самі SQL-запити)
└── schemes/            # pydantic-схеми для запитів
```

З'єднання з базою відкривається один раз, коли стартує застосунок, і закривається, коли він зупиняється (через `lifespan` у `main.py`). Усі роутери користуються цим одним з'єднанням.

Ще є `GET /`, який просто тягне всіх користувачів з бази. Я його залишив як швидку перевірку, що підключення до БД живе.

## Що ще не зроблено

Список для себе, щоб не забути:

- додати `requirements.txt` і SQL-скрипт для створення таблиць
- нормальна авторизація, зараз будь-хто може робити будь-що
- замінити одне спільне з'єднання на пул
- привести шляхи до одного стилю (`/products/add` проти `/user`)
- тести
